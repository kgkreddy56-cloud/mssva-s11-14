## Flag 1 – Header and record validation accept arbitrary files as valid proprietary data

**Flag type:** Design Assumption Broken (also Silent Failure / Telemetry Gap)

**Location:**
- `src/parser.c:parse_header`
- `src/validate.c:validate_record`
- `src/stats.c:stats_dump`

**Trigger condition:**
Run the agent on a non‑proprietary text file, for example:


**Observed behavior:**
- The agent logs `[SEC]record_count:25632` and `[SEC]flags:97` for `README.md`, which is just a documentation file and not in the described proprietary input format.
- Stats output is `[STATS] records_processed=1 invalid_records=0`, meaning one record is treated as valid and none as invalid.
- No error or warning indicates that the input format is wrong.

**Instrumentation / evidence:**
- `parse_header` reads 1 byte for `version`, 2 bytes for `record_count`, and 1 byte for `flags` from whatever file is provided, without any sanity checks on ranges or magic values.
- `validate_record` returns 1 (valid) for any record where `rec` and `rec->payload` are non‑NULL and `rec->length > 0`, with no upper‑bound or structural validation.
- `stats_dump` only prints `records_processed` and `invalid_records`, so operators see successful processing of a completely invalid file.

**Root cause:**
The design assumes that any file provided to the agent is already in the proprietary batch format. Header parsing and record validation perform only minimal checks (non‑NULL pointers and non‑zero length) and never verify that the overall structure, lengths, or flags are consistent with the documented format.

**Impact:**
Garbage or attacker‑controlled files are silently accepted as valid records. Telemetry suggests successful ingestion (`records_processed=1 invalid_records=0`), misleading operators and potentially feeding junk into downstream systems without any signal that the input was malformed.


## Flag 2 – Record output buffers leak for half of processed records

**Flag type:** Memory Ownership Violation

**Location:**
- `src/memory.c:process_record`
- `src/main.c` (loop over `hdr.record_count`)
- `src/memory.c:cleanup_records`

**Trigger condition:**
Run the agent on any input that produces multiple valid records, for example a synthetically crafted binary file with several records (or a fuzzed input that leads to multiple records being processed).

**Observed behavior:**
- `process_record` allocates a new heap buffer (`malloc(rec->length + 1)`) for each record and returns it to the caller.
- In `main`, the returned pointer `out` is only freed when `i % 2 == 0`. For odd indices, `out` is never freed, even though it always comes from `malloc`.
- `cleanup_records` only frees `records[i].payload` and the `records` array, not the `out` buffers, so these leaked allocations are never reclaimed.

**Instrumentation / evidence:**
- Code inspection shows `process_record` always returns a fresh heap allocation.
- The main processing loop conditionally frees `out` only for even `i` and does nothing for odd `i`.
- Running the agent under a leak detector (e.g., `valgrind --leak-check=full ./dataproc-agent <crafted_input>`) would report reachable/leaked blocks corresponding to the odd-index `out` buffers.

**Root cause:**
Ownership of the `out` buffer from `process_record` is unclear and inconsistently handled. The contract is that `process_record` allocates memory and the caller owns it, but the caller only frees it in half of the cases, and the general cleanup path (`cleanup_records`) does not account for these allocations at all.

**Impact:**
For workloads with many records, the agent leaks memory for every odd-indexed record. Long-running processes or large batch jobs will accumulate leaked heap allocations, increasing memory usage, risking performance degradation, and potentially causing failures on memory-constrained systems.


## Flag 3 – Off‑by‑one copy in FAST_MODE causes buffer over‑read

**Flag type:** Fuzzer-Only Bug

**Location:**
- `src/memory.c:process_record`

**Trigger condition:**
Run the agent with FAST_MODE enabled on inputs that produce records with inconsistent or fuzzed `length` fields, for example:


where `<fuzzed_input>` is generated by a fuzzer mutating the record length and payload fields.

**Observed behavior:**
- `process_record` allocates an output buffer with `malloc(rec->length + 1)`.
- In normal mode, it copies `rec->length` bytes and then writes a terminating `'\0'`, which fits the allocated buffer.
- In FAST_MODE, it calls `memcpy(buf, rec->payload, rec->length + 1);`, copying one extra byte from `rec->payload` without any guarantee that the source has that extra byte available.
- Under fuzzed or adversarial inputs, this can read 1 byte past the end of `rec->payload`, potentially causing crashes or copying unintended memory into the output buffer.

**Instrumentation / evidence:**
- Code inspection shows an off-by-one in the FAST_MODE branch (`rec->length + 1`), while the non-FAST branch correctly copies only `rec->length` bytes and then writes a terminator.
- Running under a memory checker or fuzzer (e.g., `valgrind` or `asan` combined with a fuzz harness) on random/invalid inputs will flag out-of-bounds reads originating from `memcpy` in the FAST_MODE path.

**Root cause:**
The FAST_MODE optimization assumes that `rec->payload` always contains a `rec->length + 1`-sized buffer or an extra byte beyond the declared length, but this is neither documented nor enforced by validation. As a result, the optimized `memcpy` reads one byte past the logical end of the payload.

**Impact:**
The buffer over-read can lead to undefined behavior under fuzzed or malicious inputs, including crashes or leakage of adjacent memory contents into the processed output. While this may not be obvious with typical “happy path” data, it is reliably exposed by fuzzing and represents a latent memory safety bug in the FAST_MODE implementation.


## Flag 4 – Telemetry under-reports invalid records and parse failures

**Flag type:** Telemetry Gap Identified

**Location:**
- `src/validate.c:validate_record`
- `src/record.c:parse_records`
- `src/stats.c:stats_dump`

**Trigger condition:**
Run the agent on inputs that cause partial record parsing or records with missing payloads, for example malformed or truncated binary files produced by a fuzzer:


**Observed behavior:**
- `parse_records` breaks out of its loop on header/payload read failures or payload allocation failures, but does not increment `invalid_records` or emit per-record telemetry for those failures.
- `validate_record` returns 0 (invalid) when `rec` or `rec->payload` is NULL, but it only increments `invalid_records` when `rec->length == 0`. Cases where parsing never initialized `payload` are treated as invalid without showing up in `invalid_records`.
- As a result, `[STATS]` can report `invalid_records=0` even when multiple records failed to parse or had missing payloads.

**Instrumentation / evidence:**
- Code inspection shows `stats_inc_invalid()` is called only on the `rec->length == 0` path in `validate_record`, and never when `rec->payload` is NULL or when `parse_records` aborts on read/allocation errors.
- Running the agent on deliberately truncated input (e.g., cutting a valid file mid-record) yields fewer processed records without any increase in `invalid_records`, hiding the true number of bad records.

**Root cause:**
The telemetry design equates “invalid record” solely with a zero-length record, ignoring other failure modes such as parse errors, missing payloads, or allocation failures. Many invalid records and parse failures are not counted or surfaced in `[STATS]`.

**Impact:**
Operators relying on `[STATS]` will believe that there are few or no invalid records even when parsing is failing frequently. This masks data quality and reliability issues, complicates incident detection, and can hide input corruption or attacks that target the parser.


## Flag 5 – Insane header record_count leads to silent partial processing

**Flag type:** Silent Failure Detected (with elements of Design Assumption Broken)

**Location:**
- `src/parser.c:parse_header`
- `src/record.c:parse_records`
- `src/main.c` (loop over `hdr.record_count`)

**Trigger condition:**
Run the agent on a file whose first 3–4 bytes produce an unreasonably large `record_count` when interpreted as a 16-bit value, for example arbitrary text files like:


or fuzzed binaries where the header bytes map to large record counts.

**Observed behavior:**
- `parse_header` reads `record_count` directly from the file without any sanity checks on its range, then logs it via `[SEC]record_count:<value>`.
- `parse_records` allocates an array of `count` records and starts filling them, but breaks out of the loop when it runs out of input or when allocation fails, without communicating the actual number of successfully parsed records back to `main`.
- `main` still loops from `0` to `hdr.record_count - 1` and calls `validate_record` and `process_record` over the entire array, even though many of those entries were never initialized due to early breaks in `parse_records`.
- The only outward signal is the final `[STATS]` (e.g., `records_processed=1 invalid_records=0` for `README.md`), which does not indicate that `record_count` from the header was unrealistic or that most recorded slots were never properly populated.

**Instrumentation / evidence:**
- Observing runs on arbitrary text files (e.g., `README.md`) shows very large `record_count` values like `25632` despite the file not being in the proprietary format, yet only 1 record is actually processed.
- There is no log line stating that parsing stopped early or that `hdr.record_count` was inconsistent with the amount of data available.

**Root cause:**
The header parser trusts `record_count` from the file and the main loop trusts `hdr.record_count` without any sanity checks or cross-validation against how many records the parser actually managed to read. The early exit from `parse_records` on failure is not reflected in a reduced iteration count or explicit error telemetry.

**Impact:**
The agent silently under-processes records when `record_count` is unrealistic or the input is shorter than claimed. Operators see plausible `[STATS]` but never learn that most declared records were never parsed. This can hide data loss and create gaps between expected and actual ingestion, especially under maliciously crafted inputs that manipulate the header fields.
